# G1 · FAST-LIO 建图 + Nav2 常规导航（自研运控）

本目录支持建图、普通导航和推车导航。推车导航复用已经在 Viser 测试的高层策略、Balance/Homie 下层策略和 Dex3 控制，不自动对接小车。

小车任务速度范围统一读取 [`config/pushcart_navigation.json`](config/pushcart_navigation.json)：
vx `[-0.2, 0.6]` m/s、vy `[-0.3, 0.3]` m/s、wz `[-0.4, 0.4]` rad/s，采用小车自身坐标系。
推车控制器（RPP，只输出 vx≥0 与 wz）、UDP 转发和推车原始任务指令共同遵守这些范围；导航本身不再产生横向速度，vy 范围留给高层策略和手动推车。
导航部署显式允许 `vy ±0.30 m/s`；V81/V82 导出元数据仍记录训练范围 `vy ±0.25 m/s`，不把扩大的部署限幅视作已完成真机验证。
导航时小车航向保持默认关闭（`config/pushcart_navigation.json` 的 `cart_heading_hold_kp: 0`）：RPP 已经按路径闭环管理小车航向，2026-10-21 实测航向保持（Kp=1）与 RPP 角速度同向叠加（相关 +0.72），把任务 wz 标准差从 0.054 放大到 0.085，推车学生再放大约 2.24 倍成为机身左右摆。需要时可设为 0–2 重新启用；Viser 手动推车仍使用 Kp=1。启用时的行为为——任务进入学生前，复用 Viser 的小车航向保持：参考积分原始任务 wz，测量取 IMU yaw 加相机相对 yaw；
Kp=1.0，修正上限 ±0.15 rad/s、误差限幅 ±0.3 rad，修正后任务 wz 限于训练范围 ±0.6 rad/s。
这些限幅独立于 Viser 手动推车范围，也不改变高层生成的机器人速度范围；网页的巡航速度另限制平移合速度。

- **建图**仍用宇树本体运控：用遥控器/官方应用让 G1 行走，FAST-LIO 只读雷达和 IMU。
- **导航**不再调用宇树 `LocoClient`。Nav2 做上层路径跟随（普通行走 DWB、推车 RPP），普通模式的 `/cmd_vel` 交给 Balance/Homie，并使用独立参数的骨盆航向外环；推车模式先进行小车任务航向保持，再交给推车学生，由其输出直接驱动下层策略。两种模式复用 `Viser/core` 控制器；Viser 网页仍用于本体运控测试，普通手动保向行为不变。

```text
Nav2 /cmd_vel ─ g1_cmd_vel_udp（限速 + 运动门租约 + 250 ms 超时）
   └─ UDP v3 127.0.0.1:39002（含模式代次和原始命令接收时间）─ locomotion/g1_locomotion_executor.py
         └─ Viser/core Controller：0.4 s 时间常数滤波、航向 PID、命令范数低于 0.05 即切 Balance
               └─ G1Deploy_BalanceHomie/build/g1_control（C++ 200 Hz）─ rt/lowcmd
   运控状态 ─ UDP 127.0.0.1:39005 ─ 网页桥（运控未进入策略运行时运动门不会打开）
```

## 实时性：CPU 分区、暂停与取消

**CPU 分区（无需 root）。** 机身策略控制线程与 200 Hz C++ 桥接固定在 CPU 6–7；推车相机检测及其机身反馈子进程固定在 CPU 4–5（AprilTag 检测使用与相机核数相同的 2 个 OpenCV 线程，结果与单线程逐位一致）；导航相关进程固定在 CPU 0–3。其中 FAST-LIO 及其输入路径（`livox_adapter`、`cart_navigation` 车体过滤/位姿配对）、`bt_navigator`、`planner_server`、`controller_server`、速度门和关节反馈桥保持普通优先级，直连雷达驱动、其余点云 Python 节点、网页桥和 AMCL 降为 nice 5。2026-10-20 23:04 推车时 `cart_navigation` 仍为 nice 5：50 Hz 定时只跑到 11–21 Hz、每帧过滤 24–44 ms（离线同规模 5 ms），位姿从测量到发出中位 0.35 s；同日只读空载（未抓车）为 35 ms。`TIMING cart_navigation` 的 `latency_*`、`cloud_wait`、`pairing_wait` 记录这条链路各段延迟。FAST-LIO 在 ARM 上启用 2 线程 OpenMP（原版只在 x86 上启用）。AMCL 的定位扫描限流为约 10 Hz，避障扫描仍为 50 Hz：2026-10-20 06:01 实测 50 Hz 扫描全部送入 AMCL 时，CPU 0–3 过载，FAST-LIO 实际输出约 15 Hz、里程计年龄中位 0.28 s，AMCL 位姿落后 0.3–0.7 s。C++ 桥接在 100 ms 内未收到策略指令即阻尼（`policy heartbeat timeout`），因此相机不能与控制线程共用核心：相机全速约 48 Hz、每帧 15–35 ms，与控制线程挤在同 4 核时出现过站立中心跳超时摔倒。实测 Viser 推车时相机约 45–48 Hz、观测年龄中位 0.04 s；导航中只有 25–35 Hz、帧龄 75–100 ms。2026-10-20 复测确认瓶颈是全图 AprilTag 搜索本身（同一推车画面下 b746809 原代码也只有 38–39 Hz，在 CPU 0–3 加满计算或内存带宽负载不改变帧率），现在检测只搜上一帧小车标签附近的 8 px 对齐窗口（与全图角点一致，丢失即同帧全图重搜），每帧约 7 ms、检测达到相机的 60 Hz，详见 `carmer/apriltag_detector.py`。可用环境变量 `G1_NAV_CPUS`、`G1_NAV_NICE`、`G1_EXECUTOR_CPUS`、`G1_CAMERA_CPUS` 调整；常驻的 `~/dds_bridge`（Wi-Fi 话题转发，4 个 systemd 用户服务，静止时也约占 1 核且不绑核，会挤占相机与策略核）由 `run_navigation.sh` 在导航期间暂停，退出（含 Ctrl-C）时按原状态重新启动；`G1_KEEP_DDS_BRIDGE=1` 保留它。其 wifi_to_robot 方向会向机器人 DDS 网络发布，导航期间暂停也避免了与本仓库运控并存。

**默认 20 Hz 雷达、20 Hz 路径控制。** 推车学生、Balance/Homie 和 C++ 桥接仍为 50/50/200 Hz；Nav2 指令进入执行器后经过 0.4 s 时间常数滤波，外环 50 Hz 对机身没有可见差别，却占用导航核心（实测 FAST-LIO 与点云过滤在 50 Hz 输入下只跑到约 25 Hz）。因此 `direct_livox_hz` 默认 20（可选 10/20/50），`controller_frequency` 与局部代价地图更新均为 20 Hz；RPP 加速度限幅按控制周期换算，仿真长路径回归在 20 Hz 与 50 Hz 下的最大路径偏差、到点误差一致（如 90° 折角 9.6 cm 对 9.8 cm）。`direct_livox` 默认开启（MID-360 直连，20 Hz 时每帧约 1 万点，50 Hz 时约 4000 点）；`direct_livox:=false` 回到宇树 10 Hz、每帧约 2 万点。10 Hz 时每帧时间戳为扫描开始时刻，到达时已约 0.1 s，驱动偶尔连丢两帧。单个 20 ms 帧只覆盖 MID-360 非重复扫描图案的一部分，投影成 720 格扫描后大量方向为空，地面拟合点也不足；`cloud_obstacle_filter` 因此把最近 100 ms（`accumulation_window`）的帧按各自时刻的 `odom` 位姿合并到最新帧坐标后再做地面分割，输出与输入同频、时间戳为最新帧。FAST-LIO 仍逐帧使用原始点云。20 Hz 时窗口内为两帧，10 Hz 输入时只有一帧，行为不变。

**就绪判定。** 里程计、车体过滤点云和避障扫描按“上一份新数据被接收至今”判断（0.5 s）；采集年龄另设 1.0 s 上限，只用于拒绝明显过时的测量，不再与处理和帧周期叠加后卡 0.5 s。小车/腰部几何优先按测量时刻插值；短暂缺口时用 100 ms 内最近的真实样本，不因一次配对缺失停住整条里程计。相机航向与图像时刻的骨盆反馈对齐窗口为 60 ms（覆盖一次滑拍的 50 Hz 反馈）。

**暂停与取消。** 导航参考或运控短暂未就绪（传感器抖动、相机保持、航向重新对齐、上肢增益切换）只**暂停速度**：速度门立即发零速，机身继续站立策略，网页继续续租；恢复后收到新的 `/cmd_vel` 即继续，无需重新开门。持续 3 s 未恢复才取消任务并关门。运控离开 POLICY（阻尼、故障、L2）或执行器离线仍在 0.6 s 内关门；网页桥失联 3 s 后速度门租约到期。网页地图渲染在独立线程，不阻塞安全回调。

**策略指令迟到。** 导航与 Viser 共用同一个 `Controller` 和 C++ 桥接。策略线程超过 0.1 s 未下发指令时，桥接保持最后腿部目标并切到 Balance 站立增益，2 s 内恢复则继续运行，超过 2 s 才阻尼；过温、电机报错、倾角、反馈超时、L2 仍立即阻尼。`launch.log` 中 `POLICY HOLD` 来自桥接，`CONTROL TICK late` 来自 Python 控制线程，二者按时间对照即可看出卡顿位置。2026-10-20 04:27 的掉落即为此前的 `policy heartbeat timeout`（站立 36 s、无导航动作时控制线程超时 100 ms）。

## 推车流程与坐标

1. 选择能接近小车把手的准备姿态，按顺序接管、准备、启动 Balance/Homie。确认机器人落地站稳后，再设置 AMCL 初始位姿并等待定位就绪。
2. 人工摆入小车，在“推车策略”面板明确点击抓握；可调整、加载、保存双手抓握参数及切换补偿，沿用 Viser 的限制和配置文件。
3. 在“推车策略”的“小车位姿计算方式”中选择估计方式，点击“应用并保存位姿方式”，再启动小车相机。默认的抓握估计可摆正小车后进行航向归零；AprilTag 视觉模式按标签安装方向确定车头，无需航向归零。等待 ID 0/1 的有效观测和高层观测历史就绪，点击“启动推车策略”。
4. 页面变为“小车中心导航”后，等待过滤后的扫描与导航参考点就绪，再打开运动门、设置小车中心目标。地图同时显示机器人、小车估计中心和包含两者的碰撞轮廓。
5. 停止导航并归零后可退出推车策略；松手、移开小车后点击“恢复普通导航”。退出高层不会自行把仍抓着的小车解释为普通步行。模式切换关闭运动门并丢弃旧速度，需要重新开门。

`map -> odom -> base_nav` 的 FAST-LIO/AMCL 定位链保持机器人基准。导航使用 `nav_control`：普通模式与 `base_nav` 重合；推车模式位于小车中心，其朝向为机器人世界 yaw 加相机实测相对 yaw。小车相对骨盆的位姿有两种来源：

| 网页选项 / 配置值 | 位置与朝向的计算方式 |
| --- | --- |
| 固定抓握（假设双手无滑移）/ `grasp`（默认） | 根据实时手臂关节角、手掌与把手偏置推算车中心，假设手与把手之间没有滑移；朝向仍由 AprilTag 航向观测提供，支持手动航向归零。把手和手掌偏置读取 `../Viser/config/cart_display.json`。 |
| 视觉 AprilTag（真实小车参数）/ `apriltag` | 用 ID 0/1 的原始角点和真实标签安装位置联合 PnP 求位姿，复用 `../carmer/cart_pose_measure.py --extrinsics urdf` 的同一套实现。URDF 相机外参加拍摄时刻的腰 yaw 得到物理 pelvis 下的位姿，再按 IMU 重力方向转换为水平 pelvis 坐标。位置不依赖手掌是否滑移；导航和推车高层使用同一视觉朝向。 |

相机采集采用 V4L2 驱动帧时间戳，不再把读图完成时刻当成拍摄时刻。本机只读采集测得约 59.5 Hz，同时读图完成比驱动帧时间晚约 16.7 ms；高帧率不能消除这种时间偏差。`camera-latency-ms` 仅用于另行标定的剩余偏差，默认 0。机器人反馈仍以本机接收时间为采样代理；这套历史匹配属于软件时间对齐，不是硬件同步。

固定抓握的几何计算与 Viser 显示使用相同的手掌、把手偏置。导航先按图像采集时间匹配骨盆 IMU 航向，再将相机相对角转换到当前骨盆坐标，避免直接叠加旧图像与当前骨盆摆动。跨越 ±180° 时按最短角插值；缺少时间匹配的反馈时等待有效观测，且不更新图像的原始有效期。该转换只用于导航几何，高层学生仍接收原始相机观测。

视觉模式的小车原点在顶层载物板中心正下方的地面，X 朝车前方、Y 朝相机看过去的左侧、Z 向上。载物板长 0.90 m、宽 0.50 m、高 0.775 m，含前后把手全长 0.95 m；10 cm 标签的中心为 ID 0 `[-0.103, 0.149, 0.775]`、ID 1 `[-0.103, -0.141, 0.775]` m。两标签可见时联合求解，也接受通过重投影误差与平面歧义检查的单标签结果。实现集中在 `../carmer/cart_pose.py`；使用 URDF 外参，不读取用户提供矩阵的 `provided` 模式。

更换位姿方式前，先停止导航、等待归零并退出推车策略。切换经过控制线程确认后写入 `config/pushcart_navigation.json` 的 `pose_source`，下次启动自动恢复；切换会清空高层观测历史、使旧导航速度失效并重新准备导航参考和代价地图，需要重新启用推车和运动门。接口为 `/api/locomotion?action=cart_pose_source&source=grasp|apriltag`，实际生效值在 `/api/status` 的 `locomotion.cart.pose_source`。

两种方式均允许短暂丢帧。视觉模式缺标签、位姿被拒绝或机器人补偿反馈不可用时，保留上一帧有效的完整位姿、yaw 和原始采集时间；无效帧不会延长有效期。距离最后一次有效采集超过相机超时阈值（默认 0.3 秒）后，推车观测失效、速度归零，本体策略继续站立。恢复有效帧后显示“相机航向已恢复；推车仍暂停，请归零后重新启用”；不会自动恢复之前的运动。状态区分未识别到标签、帧处理或传输延迟、新帧停止更新，并提供相机帧年龄和检测耗时；`CAMERA` 日志保留相机的帧率、耗时及标签报告。视觉模式始终使用视觉位姿，不自动回退到抓握估计；尚无有效位姿或刚切换方式时，需要等待新的有效帧。

导航启动的同一个相机进程同时输出航向与完整视觉位姿，无需另开测量程序或占用第二路相机。更新代码后需正常停止并重新启动导航，以加载新控制代码和相机启动参数；不要同时运行独立的 `cart_pose_measure.py` 占用相机。

导航相机的检测降采样倍数在 `config/pushcart_navigation.json` 的 `camera_quad_decimate` 设置，默认 `2.0`（未填写时也按 `2.0`），远处或较小的标签漏检时可改成 `1.0` 或 `1.5`，允许不小于 1 的有限数值。修改后需正常停止并重新启动导航程序生效。独立运行 `carmer/apriltag_detector.py` 则使用 `carmer/apriltag_config.json` 的 `quad-decimate`，也可用命令行 `--quad-decimate 2` 覆盖。

导航启用推车策略期间，如果一个检测帧中 ID 0、1 都未被识别，相机异步保存该帧的原始 PNG 和同名 JSON 到 `nav/log/missing_tags/<UTC时间_进程号>/`。只有背景标签也属于小车标签丢失；只看到 ID 0 或 ID 1 时不保存。JSON 包含原图帧号、拍摄时间的 monotonic 时间戳、检测到的 ID、帧率、处理耗时、检测参数及航向/位姿/IMU 补偿结果，可与导航日志对齐。以图像拍摄时间判断是否处于推车阶段，因此引发退出推车的丢标签帧仍能保留；普通行走、准备及退出后的图像不持续记录。文件写入使用独立线程和 32 帧队列，队列满或磁盘写入失败只报告 `MISSING_TAG warning`，不阻塞控制或相机检测；保存路径也以 `MISSING_TAG saved` 写入 ROS `launch.log`。图片保留供人工检查，不自动删除。

推车局部控制器 `CartPush` 改用 Nav2 Foxy 官方的 **Regulated Pure Pursuit（RPP）**，不再使用 DWB。推车任务只要求沿全局路径走，不需要局部绕障；RPP 在全局路径上取前视点（carrot），按圆弧曲率给出 `vx` 与 `wz`，不倒退、不侧移，比 DWB 的采样评分更直接地贴合全局路线。避障仍由全局规划（含实时障碍层，行为树 1 Hz 重新规划）负责，局部只做碰撞停车。推车行为树仍只做等待、重新规划，不自动执行后退/旋转脱困。组合轮廓由小车模型（含万向轮活动范围）、双手位置和普通导航的机器人轮廓组成，随当前相对位置与航向更新；默认不叠加额外余量，正向抓握时宽度约 0.70 米。继续使用 0.65 米膨胀半径和 4.0 衰减系数。

`unitree_nav2_core::CartPurePursuitController` 直接继承官方 `RegulatedPurePursuitController`（0.4.7），追踪律、曲率/代价调速和原地转向不变，只补 Foxy 版缺少的部分：

- **全局路径预处理**：Foxy NavFn 只有 `tolerance/use_astar/allow_unknown`，输出点距不均、有一格左右的锯齿、中间点没有朝向。适配层收到路径后按 2.5 cm 等间距重采样，用 ±0.10 m 滑动平均平滑两遍（等效 ±0.2 m 三角核，起终点不动），再等间距重采样，中间点朝向取切线、终点保留目标朝向。±2.5 cm 锯齿平滑后横向残差小于 5 mm；90° 直角被向内倒圆约 5 cm（再平滑会切角更多，RPP 的 0.5 m 前视点本身也会把拐角圆滑掉）。参数 `path_resolution`、`path_smoothing_distance`。
- **重规划滞回**：行为树每 1 秒重算一次全局路径。目标不变、新路径从 0.7 m 到 3.7 m 段（不近于最短前视距离）离当前路径不超过 5 cm 时继续用当前路径，前视点不会因每次重算的细微差异而跳动；真的改道（新障碍、小车被推离路线）会超过阈值并切换。参数 `path_keep_tolerance`、`path_compare_start`、`path_compare_length`。规划、控制、到点判断都以 `nav_control`（推车时为小车中心）为参考点。
- **网页速度实时生效**：Foxy RPP 只在配置时读一次 `desired_linear_vel`；适配层每拍按 `CartPush.navigation_speed` 设定（YAML 中的 `desired_linear_vel` 不使用）。纯追踪总以该速度为目标，自动调速与固定巡航在推车中行为相同。
- **末段减速**：按到**最终目标**的距离，从 0.80 m 起把速度上限线性降到 0.15 m 处的 0.10 m/s，与原推车一致；官方 `use_approach_linear_velocity_scaling` 关闭。速度高于约 0.45 m/s 时减速起点提前，保证所需减速度不超过 0.3 m/s²（0.60 m/s 时从 1.15 m 开始）。
- **开环爬升**（`closed_loop: false`）：官方加速度限制以实测速度为基准，执行器的 0.4 s 滤波和小车速度估计的滞后会让它起步过慢；改为从上一拍指令按 0.3 m/s²、0.4 rad/s² 爬升，暂停 0.25 s 以上从零开始。
- **角速度限幅保持曲率**：|wz| 超过 `max_vel_theta`（来自 `pushcart_navigation.json`，0.4 rad/s）时 vx 与 wz 同比缩小，不改变追踪圆弧。
- **指令平滑**：纯追踪 wz = vx × 曲率，官方没有 wz 变化率限制，切换到原地转向时 vx 还会直接跳到 0。适配层在所有模式下限制每拍变化：vx 0.3 m/s²、wz 0.6 rad/s²（执行器的 0.4 s 滤波不限制 wz 本身）。0.4 rad/s² 会拖慢追踪闭环，起点偏离 25 cm 时 1 m 后仍偏 8 cm，因此取 0.6。末段原地转向按 √(2×0.6×剩余角) 减速，最低 0.10 rad/s（`min_rotate_vel`）。
- **整车轮廓碰撞检查**：官方只检查小车中心点，而车头在中心前约 0.6 m；适配层沿指令圆弧检查未来 1.5 s 的完整组合轮廓，碰到致命栅格即令控制器失败，`controller_server` 发零速，行为树等待并重新规划。

主要参数（`nav2_foxy_g1.yaml` 的 `CartPush`）：前视距离 = 指令速度 × 2.5 s，限于 0.7–1.1 m（0.30 m/s 时 0.75 m）。2026-10-20 23:04 实测：小车航向跟随 RPP 角速度约有 0.85 s 滞后（RPP→机身指令 0.6 s：推车学生训练内置的任务参考滤波 `ref_alpha=0.05`（50 Hz 下 τ≈0.39 s）与 Homie 指令滤波 `cmd_alpha=0.133`（τ≈0.14 s）及学生响应；推车模式下学生直接接收原始导航指令，Viser 的 0.4 s 指令滤波只用于普通行走和停车减速；机身指令→测得小车转向 0.3 s，主要是约 0.25 s 的导航位姿年龄），原 1.5 s / 0.5–0.9 m 前视下形成 ±0.45 rad、±0.25 m、周期约 8 s 的蛇行；小车位姿本身的快速抖动只有 0.03 rad（骨盆摆动与相对航向相关 −0.93，基本抵消）。`cart_rpp_regression` 的 `test_response_s`/`test_dead_time_s` 用拟合值 0.4 s + 0.4 s 复现该滞后，新前视下直线转向反复 0–1 次（原 3–5 次），弯道最大偏差约 15–17 cm；前视点偏离车头超过 45° 时以 0.30 rad/s 原地转向（起步和急弯）；进入 0.15 m（`goal_dist_tol`，不得大于到点范围，否则会在到点范围外一直原地转）后原地转到目标朝向；曲率半径小于 0.9 m 时降速，靠近障碍（中心代价换算距离小于 0.6 m）时降速，最低 0.10 m/s。到点范围仍为 15 cm / 10°。

长路径回归 `test_cart_rpp_turns.py` 通过原生 C++ 驱动加载本机安装的 Foxy RPP 和生产配置的 `CartPush`，空地图、0.4 s 速度响应的简化车辆、50 Hz。路径先直行 1.4 m，再经 R0.6 圆弧、左/右 90° 折角或 60° 折角，最后直行 3 m，整体旋转 0–1.2 rad；0.30 m/s 下实测最大路径偏差：圆弧 3.5 cm、60° 折角 7.2 cm、90° 折角 10.2 cm，全部到点（15 cm / 10°）。直线在 0.20/0.35/0.60 m/s、起点偏离 ±25 cm 下都收敛到点且不超调；输入改成 NavFn 式路径（±2.5 cm 锯齿、三分之一点随机丢弃、无中间朝向、每秒从当前位置重规划）时，只接受 1 次路径，wz 总变化量（Σ|Δwz|）由不处理时的 4.8–5.9 降到 0.6–1.9，接近干净折线的 0–1.7；所有场景每拍 |Δvx| ≤ 0.006、|Δwz| ≤ 0.012；另有路径上障碍场景，检查在轮廓碰到障碍前停车（含 0.4 s 滞后）。`test_cart_stack.py` 用真实 `controller_server` 检查地图/里程计变换、速度读回、偏离/偏角/延迟/噪声场景和车尾障碍拒行。纯追踪没有横向自由度：起点偏离 25 cm 时车头会先转向路径约 0.4 rad 再回正。这些测试不模拟脚轮接触、滑移和推车策略的物理闭环，仍需实测。

每次启用推车策略到关闭，执行器自动在 `CWC/Data/<本地时间>_nav/` 保存一份分析数据。策略、电机和双手数据复用同一次推理的控制桥接反馈，通常 50 Hz，由后台线程写盘，不启动独立电机采集进程；另存相机标签结果、FAST-LIO `/Odometry`、`/Odometry_base` 实测速度和 Nav2 原始 `/cmd_vel`，均按同一 monotonic 时钟对齐，不录制相机视频。三路 ROS 数据在现有 `navigation_web_bridge` 进程中按消息实际频率记录，复用机身里程计回调，后台线程处理格式化和写盘，不启动独立 ROS 记录进程。`pushcart_data:=off` 关闭这套数据记录。更新后完整重启导航即可加载新的进程结构。格式与对齐方法见 [数据记录说明](../Data/README.md)。

推车运行时，现有 ROS 日志每 0.1 秒记录 `Navigation sample`（位姿来源、相机新鲜度、相对航向、小车速度估计和实际转发指令）。推车 RPP 发布 `/received_global_plan`（小车坐标系下的局部路径）、`/lookahead_point`（前视点）和 `/lookahead_collision_arc`（当前指令的预测圆弧，网页显示为局部路径），可按时间戳与导航输入对照。

推车模式的原始点云先按小车模型的板、杆、轮等几何剔除自体点，再进入 FAST-LIO，继而用于定位和避障。原始点云按逐点时间划分为 5 ms 小组，匹配采样时刻的雷达安装变换、机身姿态和小车位姿；安装变换保留关节采样时间，不能给旧反馈换上新时间戳。时钟对齐直接使用雷达 IMU 发布的 `/g1/lidar_clock`，不依赖过滤后的里程计。相机反馈晚到时按顺序等候最多 0.2 秒；无法匹配则放行实际回波供定位恢复，并暂停推车避障就绪状态。AprilTag 模式的手臂和机身姿态也使用图像时刻的历史反馈。

过滤观测过期只撤销对应就绪状态，节点继续发布状态并等待新观测恢复。网页按导航参考报文的原始发送时间计算新鲜度；超过 0.5 秒未更新时显示“导航参考状态已超时：过滤节点未更新”，不沿用缓存中的“已就绪”。缓存观测的年龄随时间增长，诊断日志使用同样规则。感知断流仅停止导航速度，不发送本体阻尼停止指令。

导航专用的 `/g1/lidar_mount` 每 5 ms 最多发布一条真实反馈样本，接收队列保留 100 条，位姿历史按时间保留完整 1 秒，避免原始关节反馈超过 1 kHz 时挤掉仍在等待相机几何的点云所需样本。这不降低关节控制、底层反馈或里程计内部关节历史的频率；仍拒绝跨越超过 50 ms 的反馈缺口进行插值。

安装位姿和雷达时钟由独立接收线程维护，避免点云计算堵住历史样本接收。等待小车位姿期间只准备一次逐点时间分组，在几何齐备后才变换点云。导航观测失效仅归零导航速度；当前机身反馈有效时，航向历史间隔异常也归零并继续运行站立策略，不因对齐等待撤掉机身控制。网页状态的 `locomotion.timing` 提供实际控制/策略频率、推理耗时和反馈到指令延迟，供与底层指令超时区分。

单帧无法完成车体过滤时，保留上一帧成功观测的接收时间，仍按 0.5 s 接收间隔失效；失败帧不会续期，也不会用于清空障碍。已经落在历史缺口中、后续样本无法补齐的旧里程计改用 100 ms 内最近的真实小车样本，没有则丢弃，避免阻塞后面的有效配对。

保留点的全部字段和原始传感器时间戳不变；两路扫描按各自采集时刻匹配小车相对位姿，被车体遮挡的远端射线设为无效，不能用空回波清除后方障碍。缺少匹配位姿时暂停该帧避障扫描，定位扫描保留原始回波，并报告等待扫描时刻的小车位姿。小车附近的外部点不按整块包围盒删除。基础里程计速度差分支持 5–500 ms 帧间隔，避免约 50 Hz 时被原有 20 ms 下限跳过；中断超过 0.5 秒后清零旧速度估计，等待新的连续测量。

网页的小车地图箭头读取 `map -> cart_nav` 的同一时刻 TF，与推车导航参考使用同一组配对位姿；不再将最近一条 AMCL 位姿与最新相对几何直接拼接。航向或 TF 过期时保留灰色虚线的最后位置并标明观测年龄；该位置仅用于显示，不发布到 TF、过滤或控制。恢复有效位姿后更新；脱离小车、切换位姿方式或地图后清除旧显示。导航执行器在加载时预计算固定 URDF 变换，每轮以同一份最新反馈计算一次几何并用于运动门和状态发布，避免重复解析和计算挤占控制线程。

当前吊装测试还启用了**后方吊架和扶护区屏蔽**，普通行走和推车均生效：`config/pushcart_navigation.json` 的 `gantry_filter` 定义机身 `base_link` 坐标系中 x `[-1.0, -0.5]`、y `[-0.6, 0.6]`、z `[-2.0, 2.0]` 米的区域，即身后 0.5–1 米、左右各 0.6 米。原始点云先剔除这个随机器人移动的区域，再执行小车自体过滤，进入 FAST-LIO / AMCL 和原有 Nav2 实时障碍层。这个区域内的人员、吊架及其他物体都被忽略，区域外仍使用实时雷达避障；不是只按静态地图导航。页面持续显示屏蔽范围。结束吊装测试时将 `gantry_filter.enabled` 设为 `false` 并重启导航；修改范围也需重启。

后方区域直接剔除点云并清除区域内历史障碍，不做额外的吊架遮挡判断，也不增加扫描坐标变换检查或运动门条件。原生 `ObstacleLayer` 接收 `/navigation/rear_clear`：这些专用射线从清空矩形中心出发，到矩形边缘结束，只清障、不标记，每次替换上一组射线。区域清空所需数据失效或 0.2 秒没有新清障输入时，发布空观测撤销缓存射线；后方过滤不可用时保留原始点云，恢复普通实时障碍处理，扫描继续输出。推车自身的航向、车体过滤及其他导航检查仍生效。局部和全局地图都沿用原有障碍层，静态地图障碍仍保留。清空区域跟随机身坐标，区域外的实际雷达回波继续用于避障。

两张障碍地图复用 Nav2 原生 `ObstacleLayer`、静态层与膨胀层，不另设推车障碍插件。切换普通/推车模式后，定位与实时轮廓就绪且运动门关闭时，后台主动确认轮廓并调用 Nav2 的 `clear_entirely_*_costmap` 服务，清除旧模式留下的小车回波；无需先点击开门。等待新的避障扫描和两张地图各两次发布后完成准备；开门请求复用同一把锁和同一准备流程，重建失败或模式变化会拒绝开门。扫描中的真实障碍重新标记，静态地图重新叠加，不清除导航大轮廓内的所有障碍，不伪造穿过车体的清障射线。该重建会清除动态层中已不在视野内的旧缓存，只在模式切换/桥接启动后执行，不在正在行走的任务中清图。

导航地图用小车 URDF 的车身、把手和万向轮数据绘制独立绿色图标，并按当前选择的位姿估计在地图中旋转、移动；箭头标注地图航向。机器人与小车的组合碰撞轮廓用橙色虚线单独显示，不再填充成整块色区。两者可在“显示图层”中分别开关；显示只反映几何和位姿，不改写地图或碰撞代价。

`pushcart_navigation.json` 中 `footprint_padding_m`、`tracking_margin_m`、`relative_yaw_margin_rad` 当前均为 0，缺省值也为 0。小车自体点云过滤仍单独保留 4 cm 余量，不扩张导航碰撞轮廓。视觉定位使用上述实物尺寸；碰撞轮廓、自体过滤与地图图标仍采用现有小车 URDF（车身约 1.01 × 0.55 m，含万向轮活动范围约 1.20 × 0.70 m），没有据顶板尺寸推定下层板和轮子的实际形状。模型未包含额外装载物；推车导航的实际跟踪误差和遮挡效果仍需现场验证。航向/反馈或过滤扫描过期时关闭运动门、平滑归零，机身保持原有策略支撑。

低状态 UDP 数据包已升级到 v2，含生产端 monotonic 采样时间；更新后必须完整重启导航，使关节桥、运动学、执行器和导航参考使用一致版本。

传输新鲜度按源时间判断：`/cmd_vel` 和运动授权使用 DDS 发布时间；里程计、扫描、AMCL 与网页状态保留采样/发送时间，重复、乱序、超前或过期数据不能续期。普通行走与推车都执行检查。运控操作 UDP 为 v2（24 字节，新增 monotonic 发送时间），旧版操作包被拒绝，网页桥与执行器必须一起重启。显式停止仍优先。

FAST-LIO 点云与时间戳成对存储，最多保留 3 帧且跨度不超过 250 ms；处理前丢弃超过 500 ms 的积压。跳过旧点云时仍保留中间 IMU 用于积分，IMU 缓存最多 4 秒/4000 样本；已经初始化后若积分历史真被耗尽，不猜测当前位置，暂停定位并报告需要重启定位。关节桥检查 CRC 和设备 tick，重复反馈不重新计时。SDK 关节时间仍为主机接收代理，不代表硬件同步。

点云坐标变换不再让缺少对应位姿的队首挡住后续可用帧，变换和障碍过滤均拒绝过期或倒序输出。地面估计失败且有效地面记录过期后，不发布空障碍点云冒充无障碍。Nav2 主扫描与其观测缓存期限为 500 ms，辅助清空射线在 300 ms 后自动过期（即使发送进程退出）；这些定位/感知故障经速度归零处理，不撤销机身站立策略。

小车几何失效时，原始雷达测量仍进入 FAST-LIO/AMCL，避免相机丢标签连带切断机器人定位；此时不做猜测性自体剔除，定位可能受车体回波干扰，避障扫描暂停、推车参考失效、导航速度暂停。3 秒内恢复新鲜几何与扫描时自动继续；超过 3 秒才关门，需人工重新开门并下发目标。AMCL 在未超过 2 cm / 0.02 rad 位移阈值时不会周期性输出位姿，导航中超过 0.5 秒没有新位姿会请求官方静止扫描更新；真实数据超时仍按 1.5 秒保护。故障时保留点云、扫描、里程计、AMCL 和相机各自的数据年龄与首个停止原因，定位缺输入与推车观测失效分别提示。

## 构建与启动

```bash
cd /home/unitree/CWC/nav
./build.sh            # colcon 构建 + 生成默认 cf 二维地图
./run_mapping.sh      # 建图（Viser 0.0.0.0:8080）
./run_navigation.sh   # 导航（Canvas http://<Wi-Fi IP>:8080，rosbridge 9090）
```

导航与 `Viser/run.sh` **不能同时运行**：两者都要占用部署包的底层桥接（UDP 27001/27002）和机器人低层控制。

入口脚本会在加载 ROS 环境后优先使用本机 `~/cyclonedds/install/lib` 中的 CycloneDDS 0.10.2（可用 `UNITREE_CYCLONEDDS_LIB` 指定目录）。Foxy 自带的 0.7 在当前机器人网络的 DDS 发现阶段会崩溃，表现为多个节点同时退出、8080/9090 没有监听。SDK 本体反馈桥与运控执行器独立加载各自 SDK 的 DDS 库，避免混用；ROS 网页节点使用系统 Python，不受已激活的 Viser 虚拟环境影响。

常用参数：

```bash
./run_navigation.sh locomotion_mode:=sim        # 运控使用 C++ 合成反馈；雷达/定位节点仍启动
./run_navigation.sh heading_mode:=active        # 启用导航航向外环（独立配置默认 active）
./run_navigation.sh heading_mode:=disabled      # 关闭附加航向修正，保留滤波和模型切换
./run_navigation.sh locomotion_policy:=homie    # 固定单模型（默认 auto）
./run_navigation.sh start_locomotion:=false     # 不启动运控（只看定位/规划）
./run_navigation.sh direct_livox:=false         # 改用宇树原有 10 Hz 雷达服务（默认 20 Hz 直连）
./run_navigation.sh direct_livox_hz:=50        # 直连雷达改回 50 Hz（控制器频率另在 nav2_foxy_g1.yaml）
```

**真机运行记录。** 导航启动后在第二个终端执行 `bash nav/tools/record_run.sh <名称>`，跑完按 Ctrl-C（导航可以继续运行）。结果在 `nav/log/runs/<时间>_<名称>/`：`launch.log`（本次 TIMING/CAMERA 行）、`ros_nodes/`（各节点日志）、`topics.csv`（每 2 s 的 `/cmd_vel` 与 `/amcl_pose` 条数，`/cmd_vel` 即 RPP/DWB 实际输出频率；里程计和扫描频率见 `TIMING cart_navigation`）、`cpu.csv`（每核占用与频率）、`procs.log`（每 5 s 占用最高的进程）、`git.txt`（提交、改动文件和频率配置）、`summary.txt`。记录器只订阅小消息、不发布，固定在 CPU 0–3 并降为 nice 10。`python3 nav/tools/summarize_run.py <目录或 launch.log>` 可单独重新汇总；`nav/log/runs/20261020_202243_baseline_50Hz_fullframe/` 是改为 20 Hz 和窗口检测之前的基线（相机 28.5 Hz、帧龄 86 ms，FAST-LIO 25 Hz，控制 50.0 Hz）。


`direct_livox` 默认开启。通过宇树官方服务接口暂时停用 `lidar_driver`，由本机 Livox SDK2 驱动以 `direct_livox_hz`（默认 20 Hz）采集；点云及 IMU 同时切换，保留安装外参和逐点采样时间。这里是缩短真实采集帧的时间窗口，并非重复发布旧帧或把 10 Hz 点云抽稀。原始每帧点数随数据包边界略有变化，后续过滤还会减少点数。`direct_livox:=false` 继续使用宇树原有 10 Hz 雷达服务。

2026-10-19 在本机静止采集测试中，原始点云中位数 4032 点，点云、FAST-LIO 里程计、避障及定位扫描均约 50 Hz，IMU 约 200 Hz。运动中的定位精度与推车效果仍需现场验证。

导航控制与显示分别配置：Nav2 路径控制与局部代价地图内部更新为 20 Hz，速度 UDP 转发及运控执行器接收循环为 50 Hz（重复转发最新指令，不续期）；执行器每拍同步小车几何，导航参考以 50 Hz 接收。雷达时钟通过原始 IMU 流换算为主机时间，`/Odometry_base` 保留测量时刻，不再用映射完成时间重新盖章；腰部关节、固定抓握几何或视觉位姿均按该时刻从各自历史中配对；在 50 ms 内的相邻样本之间插值，缺口时取 100 ms 内最近的真实样本，超出则视为缺少配对。不能把长时间缺帧插值成可靠运动。推车速度在世界坐标中按测量时间差分、平滑，再转回当前小车坐标；重复或倒序消息不生成新速度。点云使用同一帧的时间换算和腰部 TF。停止诊断分别记录机器人 `/Odometry_base` 的速度和控制器实际使用的 `/Odometry_navigation` 三轴速度、同帧绝对/相对航向、几何时间戳及航向时间校正量。局部代价地图对外发布仍配置为 8 Hz（实测约 7–8 Hz），网页状态保留 2 Hz，机身策略原为 50 Hz、底层伺服为 200 Hz。雷达默认 20 Hz 直连。

普通行走的 DWB 将碰撞检查放到轨迹评分末尾：非负的路径、朝向和速度评分先排除已不可能优于当前最佳轨迹的候选，所有可能被选中的轨迹仍经过原来的碰撞检查。关闭网页不使用的全候选轨迹、评分和代价点云可视化输出。三轴速度采样配置为 `9×7×11`。推车 RPP 每拍只计算一条圆弧，计算量远小于 DWB。本机早期隔离 ROS 测试中，普通与推车控制、局部地图内部更新及 UDP 新指令可达到约 50 Hz；真机整栈负载需单独验证。测试包含模拟运动、真实 ONNX 与 C++ 合成反馈，不代表已验证真机推车闭环。

真实雷达、FAST-LIO 与普通路径控制同时运行、控制输出隔离且不下发电机的短测中，控制输出为 50.02 Hz，局部地图内部更新为 50.00 Hz。控制周期的 95 分位约 23 ms，仍有偶发超周期；50 Hz 是当前实测平均频率，并非硬实时保证。

直连模式默认使用 `eth0`、本机 `192.168.123.164` 和雷达 `192.168.123.120`，依赖已构建的 `livox_ros_driver2_safe_node` 和本机 `~/unitree_sdk2_python`（可用 `UNITREE_SDK2_PYTHON` 指定 SDK 目录）。切换需要等待原服务确认停止，实测约 7 秒。正常退出或驱动异常退出时会恢复雷达原参数及服务状态；退出期间请等待 `Original lidar parameters and service restored.`，不要强杀恢复进程。若断电或强杀留下恢复记录，先确认直连驱动已结束，再在已加载 ROS 与本工作区环境的终端运行 `ros2 run unitree_nav2_web livox_source --restore`。恢复记录位于 `~/.cache/cwc_navigation/livox_source.json`，未完成恢复时会拒绝再次切换。

## 网页操作顺序

1. **PCD 地图**：选择 `maps/` 中的 PCD，生成并装载二维地图。
2. **运控与站立**：先在“模型组合”选择 **60000 轮 Homie + V8.1 高层**（默认）或 **68000 轮 Homie + V8.2 高层**；再选择上半身准备姿态，等待页面确认。吊装或扶稳后依次点 ① 接管底层 → ② 准备姿态 → ③ 启动策略。模型和姿态都可在①之后、②之前更换，开始准备后锁定；阻尼停止并复位后可重新选择。两套模型与 Viser 共用加载器并提前预热，切换同时选择行走、高层及配套估计器，选择本身不动作。机身准备不使能 Dex3，也不依赖手部就绪。
3. **落地后定位**：确认混合策略已启动、机器人已落地站稳，再拖拽设置初始位姿，等待 AMCL 显示 READY。正常运控模式下，准备姿态阶段不能提交初始位姿；程序只检查机身策略是否正常运行，落地及站稳由操作者现场判断。只读定位启动（`start_locomotion:=false` 或 `locomotion_mode:=observe`）不要求启动电机策略。
4. **导航**：选择速度模式和 0.20–0.60 m/s 的速度，点击“应用并保存速度”，看到“已应用”后启用 G1 运动安全门，再在地图上拖拽 Nav2 Goal。也可在导航中调整速度。
5. 停止：“停止 / 取消导航”会关闭运动门，按与 Viser 相同的滤波减速；自动模式在命令范数低于 0.05 的同一拍切回 Balance，并将当前策略命令置零。“阻尼停止”立即进入阻尼，会卸掉支撑力。实体遥控器 L2 随时生效。阻尼后点“复位（只读）”，再重新执行 ①②③。

运动门打开需要同时满足：地图 + AMCL 收敛 + 传感器新鲜 + **运控处于策略运行** + 速度设置已确认 + 当前模式的导航参考点就绪。运控离开策略运行（L2、阻尼、故障、进程退出）0.6 s 后，导航会自动取消、运动门关闭。

网页“运控提示”沿用 Viser 的关节参考范围检查，显示机身、双手超限及准备超时等提示；恢复后的提示保留约 5 秒并标记“已恢复”。关节角度超出参考范围不影响机身健康状态、不关闭导航运动门，也不触发全身阻尼。有限值请求目标仍限幅；位置范围与名义 PD 力矩约束冲突时只降低相关关节增益。准备超过 10 秒未到位会继续保持位置控制，等待实测到位后再手动启动策略。SDK 机身故障、非有限数值、机身反馈/底层策略心跳超时、倾角保护和显式停止仍按原规则处理；Nav2 断指令或定位丢失则取消导航并平滑归零。

网页速度作用于平移命令的合速度 `hypot(vx, vy)`，不是实际机身速度的保证值。**固定巡航**在普通路段优先选择设定速度，保留较慢轨迹供转弯和避障；**自动调速**由 DWB 自行选择不超过设定上限的速度；推车 RPP 两种模式相同，都以设定速度为目标，仅在弯道、靠近障碍和末段降速。两种模式都从距最终目标 0.60 m（普通）或 0.80 m（推车）起，把平移速度上限逐步降至 0.15 m 处的 0.10 m/s；固定巡航偏好同时逐步释放。普通行走的减速约束在 DWB 候选选择阶段生效，推车由 RPP 适配层在追踪前限制目标速度；底层仍使用 0.4 s 滤波。

到点范围为 **25 cm、朝向 20°**（2026-10-23 起；15 cm / 10° 时推车末段修正太慢。Foxy 只有一个目标检查器，普通行走同样适用），目标检查器、DWB 和推车 RPP 的位置范围一致。Nav2 确认完成后，网页桥关闭导航速度门并发送平滑归零请求；机身继续运行策略，过滤后命令范数低于 0.05 时置零并切回 Balance。旧速度不能继续微调或重新起步；等待归零结束、重新启用运动门后再下发下一目标。这里的 0.05 是 `[vx, vy, wz]` 原单位命令的数值范数，不是纯平移速度阈值。位置判定范围也不是机身最终停止误差的保证。

速度在普通导航中通过候选生成器生效（固定模式同时使用巡航评分），推车中作为 RPP 的目标速度；不在碰撞检查后放大 `/cmd_vel`。模式与速度作为一个参数事务提交给控制器，确认成功后保存到 `config/navigation_speed.json`；重启后重新确认再允许导航。首次默认是自动调速、上限 0.35 m/s。接口为 `/api/navigation/speed?mode=auto|fixed&speed=0.20..0.60`，当前确认状态在 `/api/status` 的 `navigation_speed` 中。

导航直接使用当前 Viser 的 `Controller`、`ModelSets`、Balance/Homie 模型、观测历史和底层 PD，不维护另一套停车控制器。页面显示当前模型组合；`/api/status` 的 `locomotion.model_set`、`model_sha256`、`model_warmup` 返回实际选择、文件哈希和预热状态。两套推车高层均采用导航专用任务限幅。命令按 `v += min(1, dt / 0.4) * (target - v)` 滤波；停车时从最后实际下发的命令（含已有航向补偿）向零衰减，范数低于 0.05 即置零并切 Balance。没有固定 1 秒截止，也没有归零后再等 0.5 秒的阶段；0.4 秒是时间常数，交接时间取决于起始命令大小。

运控执行器的启动输出、模型加载异常和底层桥接报错同时写入当次 ROS 启动目录的 `launch.log`（默认 `~/.ros/log/<本次启动>/launch.log`）。关闭终端后仍可检查，启动成功行包含初始模型名称和 Homie 文件哈希；后续选择以页面/API 或启用记录后的会话日志为准。

正常减速仍属于健康的策略运行，不触发上述故障取消；减速期间禁止开启运动门或提交新目标。导航零速和关门直接触发减速；上游断指令或 UDP 断流从最后一次原始 `/cmd_vel` DDS 发布时间判断 250 ms 超时，不因缓存转发续期，这与 Viser 松手检测后减速的流程一致。减速中不反向、不增加命令幅值、不产生新纠偏，不接收排队运动。交接后新的有效非零命令可重新起步。命令归零不代表实际机身已停稳。显式阻尼、实体 B/L2 和反馈故障仍立即覆盖普通减速。

定位故障、取消导航和异常退出导航任务会先关闭速度运动门，再尝试取消 Nav2 action；取消接口报错不会跳过关门。迟到的开门回执、旧的续租、正在等待轮廓确认的开门请求都不能覆盖更新的停止请求。运动门关闭只撤销导航速度授权，运控执行器继续保持策略运行，按上述滤波减速并切回 Balance。网页桥进程失联由 3 秒授权租约触发关门，速度转发进程退出由 250 ms 原始命令看门狗触发减速。

导航参考短暂失效时，UDP 转发立即清空旧速度并发出归零指令，页面显示具体的“导航暂缓”原因；同一参考模式在 3 秒内恢复时保留当前导航任务，必须收到恢复后的新速度才能继续。连续失效达到 3 秒则取消任务、关闭运动门，后续数据或旧续租不能自动恢复；模式切换和主动停止立即关闭。相机、高层策略和抓握本身的故障保护仍然有效。POLICY 状态下的暂停会显示抓握、推车启用或小车观测原因，不再误报“尚未进入策略运行”。

关门状态与发布在同一临界区完成，并发但校验失败的开门请求不能取消关门。每次重新开门会清掉速度缓存，等待新的 `/cmd_vel`；执行器也会丢弃关门前已经在途的旧速度。AMCL 或导航里程计包含非有限值、无效四元数时，按定位故障关门并平滑停车，不向底层发送阻尼停止。

**退出整个导航启动终端（Ctrl+C）、结束运控执行器或底层控制进程，会结束机身支撑，不属于“关闭运动门”。** 正常停车用网页“停止 / 取消导航”，保留运控执行器运行；要退出整套程序，应先完成停车并吊装或扶稳。底层进程崩溃、机身反馈故障不能靠上层导航保证平滑交接。

## 路径控制与骨盆航向控制

普通行走的 DWB 通过采样、预测和评分候选速度轨迹完成局部路径跟随，推车的 RPP 按前视点圆弧追踪全局路径，都不是 PID。保留它们作为上层，骨盆航向 PID 作为策略输入前的执行补偿，不再增加第二个路径 PID。

普通导航命令使用 `NAVIGATION`。进入运动时捕获当前骨盆 yaw，此后按经过滤波的导航角速度推进参考：`yaw_ref += wz_nav * dt`，误差取最短角。最终 `wz = wz_nav + bounded_PID(yaw_ref - yaw)`；D 项使用参考角速度与测量 yaw rate 的差，因此正常转弯不再被手动锁向抵消。参考偏差上限 0.20 rad，修正上限 0.15 rad/s；XY 始终使用机身坐标，不旋转、不加闭环。停车、来源切换和反馈异常会释放旧参考与积分。这样消除了两层争用固定航向的逻辑冲突，真实延迟、漂移和闭环稳定性仍需实机验证。

导航默认 `Kp=1.0, Ki=Kd=0`，目前实际只启用 P；I/D 保留可配置能力。Viser 使用自身配置。推车由同一 Controller 自动切换为 `PUSHCART` 来源，参考按高层给出的机器人 wz 推进，不能用小车任务 wz 积分。

## 与原项目的差异

- 运控改为当前 Viser 的共享实现，不再调用原 `LocoClient`、旧抓握播放器或旧推车控制器。
- 普通导航保留 `FollowPath`；推车使用独立的 `CartPush`（Regulated Pure Pursuit，只输出 vx/wz）、小车中心参考、动态组合轮廓和模型自体过滤。
- 网页包含运控和推车/抓握面板；导航停机继续复用原有滤波和模型交接。
