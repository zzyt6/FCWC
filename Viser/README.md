# G1 外层 Viser · Balance / Homie

网页入口位于 `Vender/app.py`，配置在 `config/`，测试在 `test/`，复用模块在 `core/`，工具在 `tools/`，详细说明在 `docs/`。启动入口统一为本目录的 `run.sh`，直接加载相邻 `G1Deploy_BalanceHomie` 的两套 ONNX、观测构造、控制配置和 C++ 桥接。不再依赖已删除的 `unitree_rl_gym`。部署包内原来的 `visualizer.py` 已移除。

## 启动

直接执行 `./Viser/run.sh` 默认启动真机控制模式（网卡 `eth0`、网页端口 `8086`）。网页仍需显式点击接管底层、准备姿态和启动策略后才会释放控制。

在 `/home/unitree/CWC` 执行：

```bash
# 只读同步 + 影子推理：不释放原厂控制器，不创建 LowCmd 发布器
bash Viser/run.sh --mode observe --interface eth0 --port 8086

# 真机控制：启动仍为只读，网页点击接管底层后才释放原厂控制器
bash Viser/run.sh --mode control --interface eth0 --port 8086

# 离线联调：C++ 合成反馈，不连接 DDS，不是 MuJoCo 物理仿真
bash Viser/run.sh --mode sim --port 8086
```

浏览器访问 `http://本机IP:8086`。`--host 127.0.0.1` 可限制为本机访问；端口占用会报错。三种模式共享部署包本机 UDP 27001/27002，同一时间运行一个入口。

启动脚本优先使用 `VISER_PYTHON`、`HYBRID_DEPLOY_PYTHON`、可用的当前 Conda 环境，再尝试本机 `~/miniconda3/envs/CWC/bin/python`。本机 CWC 已有 ONNX Runtime 和 Viser；不再使用旧环境的 TorchScript 推理。迁移机器时执行 `bash Viser/setup.sh`，并一起复制 `G1Deploy_BalanceHomie`、`G1_URDF` 和 `G1_Upper_Initpose`。每次启动会重新检查构建 C++ 桥接，配置摘要不一致时拒绝控制。

## 网页操作

右侧为精简的状态与操作面板（速度滑条、按住发送、航向参数；视图设置、运行记录与航向反馈默认折叠）。中间为实时三维模型，左侧为 **关节监视** 侧边栏，关节数值和详细告警统一放在左侧。
三维模型按反馈更新发生变化的关节，固定或未变化的局部节点沿用原变换；仍同步更新用于小车参考位置的双手运动学，减少网页刷新对策略线程的影响。

1. **接管网页操作**：只允许一个浏览器发送运动指令。
2. **① 接管底层**：检查反馈并释放原厂控制器，等待进入已接管状态。此时不提供姿态支撑，需要吊装或扶稳。
3. 在 **上半身准备姿态** 中选择姿态，再点击 **② 移到准备姿态**。下半身始终读取 `G1Deploy_BalanceHomie/config/deploy.json` 的 `default_q_sdk29` 前 12 项；腰 yaw 与双臂读取所选 YAML 的 `hold_target_q`，详见下表。此时不使能 Dex3、不发送手部归零指令。机身准备至少 3 秒并限制关节速度；实际机身关节位置和速度到位后才显示准备完成。超过 10 秒仍未到位只警告，保持准备目标和正常位置控制增益，不进入 FAULT、不阻尼退出。右侧提示继续保持姿态，左侧列出未到位关节；实测到位后警告解除，再手动启动策略。
4. 等待准备完成，再点击 **③ 启动混合策略**；策略速度命令与滑条均归零。
5. 调整三个滑条，再**按住发送速度**。单独拖动滑条不发速度。松开后经 250 ms 心跳超时识别，按时间常数 0.4 秒的一阶滤波减速，命令范数低于 0.05 时归零并立即切入 Balance。0.6 m/s 的纯前进命令从开始减速到交接约 0.98 秒，另计松手识别时间；这不是实测身体停稳时间。参数位于相邻部署包 `config/deploy.json` 的 `command_filter_tau_s`。
6. **速度归零**立即清零滑条和目标，让最终策略命令逐步降到零，策略继续运行；网页显示减速过程，期间无需按住发送，也不接受新的运动指令。**阻尼停止**立即中断减速、锁定停止并让桥接执行 Kp=0、Kd=2 的退出阻尼。停机后点击“接管网页操作”恢复只读反馈，再依次执行①②③，无需重启网页程序；重新接管不会自动恢复运动。

### 可选的推车流程

直接用上述 `Viser/run.sh` 即可，不需要另开高层网页。推车能力默认加载，策略默认关闭。
先启动混合策略站稳，再把小车移到手边、明确使能抓握并调好现有手指参数。
准备阶段会在后台提前连接只读相机，失败时可在“④ 可选：推车策略”点击“连接 / 重试小车相机”。
在普通混合策略下速度归零，将小车前进方向与骨盆正前方对齐并保持静止，点击“标定航向零位（车身已对正）”。
按钮采集 30 个新有效帧，航向波动不超过 3° 时应用圆周平均偏置，并显示结果；重复标定不会累加偏置。
标定只对本次运行生效，不改配置文件或骨盆 IMU。标定成功后重新积累推车历史；采集期间不能启用推车。
等航向有效、推车历史达到 32/32 帧、手部动作完成且速度归零，
再自行选择“启用推车策略”。不启用时就是原来的普通行走，相机/抓握不是普通行走的前提。

启用推车会显示训练用小车模型并切换为小车任务速度滑条。先归零，再点“返回普通行走 / 继续调抓握”
可退出高层，混合策略持续运行，当前手指角度保留。推车时锁定手部编辑，退出后恢复。
若推车中相机/抓握失效，会减速并锁住旧指令；归零后可重试或直接返回普通行走。

机身模型使用实时反馈；抓握中的手指参考模型同步当前网页抓握设定（含选中的补偿），
左侧关节表仍显示实测值。未更改抓握文件，也不采用训练资产中烘焙的手指角度。
小车航向来自 carmer；默认车体位置为双手抓握参考，标明“未标定”。
可在 `config/cart_display.json` 填入实际标签安装坐标启用测量位置。
详见 [推车说明](../G1_high_policy_deploy/README.md)。

| 上半身准备姿态 | 配置文件 | 双臂角度 |
|---|---|---|
| 姿态 1 · 原准备姿态（默认） | [`deploy_upper_hold.yaml`](../G1_Upper_Initpose/deploy_upper_hold.yaml) | 原配置 |
| 姿态 2 · 双臂下垂 | [`deploy_upper_arms_down.yaml`](../G1_Upper_Initpose/deploy_upper_arms_down.yaml) | 双肘 +90°，左肩 roll +10°，右肩 roll −10°，其余手臂关节 0° |

YAML 角度单位是弧度。第二套腰 yaw 保留原值，固定腰 roll/pitch 仍为 0。按本项目 URDF 正运动学计算，姿态 2 的上臂和前臂分别偏离竖直向下约 13°、11°，双臂略向外张开，接近自然下垂。这里肘关节 +90° 使用模型零位定义，不代表人的肘部弯成直角；该检查不等于真机碰撞或稳定性验证。

只有网页控制权持有者可以在准备前选择，选择本身不触发运动。准备请求发出后立即锁定，准备完成及策略运行期间保持所选上半身目标；同一次程序运行中重新接管保留选择。文件在启动时读取，修改后需重启 Viser。两套姿态共用原有 Balance/Homie PD 配置，Dex3 抓握仍使用原 `deploy_upper_hold.yaml`，不随上半身选择改变。日志快照保存 `prepare_pose`，`preparation_pose_selected` / `preparation_started` 事件保存选择和使用的文件路径。

持有者断开网页会停止并释放网页所有权，其他浏览器可重新接管。交给实体遥控器后：R2 接管，再按 R2 使用所选姿态准备，准备后 R2 启动策略；L1+摇杆运动、B 归零、L2 停止。实体 L2 不受网页持有者限制。

**Dex3 使用文件补偿角**：接管底层后显示此复选框，默认不勾选。勾选后，首次使能抓握及后续“Dex3 双手：抓握／松开（3 秒）”按钮的目标，均加入 `config/dex3_zero_calibration.json` 中按关节名加载的补偿角。不勾选时，归零目标为全零，抓握目标为 YAML 原始抓握角。复选框本身不触发运动，只影响下一次姿态操作；仅持有网页控制权的用户可修改，运动中或等待上一条指令确认时禁用。

补偿文件在启动时读取，目前右手 `thumb_0` 配置为 **+0.73 rad**，其余补偿为 0。文件无效、缺失或“抓握角 + 补偿角”超限时，勾选请求会被拒绝并显示原因；正常未补偿操作仍可使用。修改文件后重启程序。原来的两个独立补偿按钮已删除。

**Dex3 双手：抓握／松开（3 秒）**：接管底层、进入准备姿态及自动启动策略均不使能手部。准备完成或策略运行后，首次按钮显示“Dex3 使能并抓握（3 秒）”，明确点击时才使能，并从当时的实测角度执行抓握；未点击前不发布 Dex3 电机指令。之后使用同一个按钮切换抓握／松开。所有 14 个手指关节由 C++ 200 Hz 循环执行 3 秒五次插值；运动中重复点击不反转或重启轨迹。显示的姿态和进度表示命令状态，是否实际到位应看左侧误差。

**Dex3 抓握姿态调节**：使能后显示，三秒姿态切换完成后可用。左右手各有 7 个关节滑条，单位为 **°**，步长 0.01°；可拖动或点击数值输入。调节会实时应用整套抓握姿态，由 C++ 200 Hz 循环从当前命令角度连续跟随，每个关节最高 **0.5 rad/s（约 28.6°/s）**，接近目标时减速；松开滑条后继续到达并保持目标。跟随过程中可以继续调节。仅网页控制权持有者能操作；三秒切换期间、手部故障暂停、停止或只读模式下不可调节，编辑操作不会使能或重新启用手部。手部 PD 沿用 `config/dex3_pd.json`。

滑条编辑的是未加补偿的原始抓握角；勾选“Dex3 使用文件补偿角”时，实时下发会叠加补偿，并收紧滑条范围以确保原始角度和叠加结果都在命令限位内。改变复选框本身不动作，下一次调节、加载或姿态切换才使用新选择。之后“抓握／松开”按钮中的抓握也使用本次调节结果。

- **保存抓握姿态**：将当前 14 个原始抓握角以弧度写入 `G1_Upper_Initpose/deploy_upper_hold.yaml` 的 `hand_grasp.left/right`。只替换手指角度，保留上半身目标、PD、注释和排版。保存不触发新的动作；界面显示未保存修改、成功或失败信息。
- **加载并应用抓握姿态**：重新读取同一文件的抓握角，并立即按当前补偿选择限速应用，无需重启。下次启动也自动读取这些保存值。加载失败、角度无效或加载期间控制状态改变时保留当前目标。

文件操作在独立线程执行，保存采用临时文件原子替换，不阻塞实时控制循环。联调测试仅操作系统临时目录中的 YAML。`dex3` 遥测增加原始 `grasp`、`editing` 和保存状态；`dex3_grasp_edited` 记录修改角度及补偿选择，`dex3_grasp_file` / `dex3_grasp_file_error` 记录文件操作。

**Dex3 超限恢复**：这是独立、必须明确点击的单指动作，不由接管或准备自动触发。手指位置越界只显示警告，不阻止接管、准备或机身策略运行。接管后、尚未准备时，可以展开该区域，选择下拉框中列出的手指，再点击“恢复所选手指到限位内”，一次恢复一个手指。恢复不是进入准备的必要条件；点击机身准备会结束正在进行的手指恢复，多个手指越界可逐个恢复。

该功能使用官方 `HandCmd_` 的目标角度和 PD 控制，不是清除硬件限位或复位故障码。仅列出反馈新鲜、SDK 未报故障、越界超过 0.02 rad 反馈余量且不超过 0.15 rad（约 8.6°）、速度不超过 0.5 rad/s 的手指。目标为最近边界内侧 0.03 rad；仅所选手指有位置增益，其余手指保持零位置增益和退出阻尼。本体保持未准备状态。恢复 Kp 从 **0.5** 在 **1 秒**内线性增加到 **2.0**，Kd=0.1；旧的 0.08 Nm 计算力矩限幅已移除，避免将 Kp 再压低到要求范围之外。位置进入目标 ±0.01 rad 且速度不超过 0.05 rad/s，持续收到 150 ms 的到位反馈后结束。

恢复最多持续 **3 秒**。超时、手部反馈无效或超过 200 ms、恢复指令超过 250 ms、进一步向外越界或速度超过 0.5 rad/s 时，仅结束这次手指恢复，撤掉位置增益并显示警告，不调用机身全局停止，也不需要重新接管。失败不会自动重试；可明确发起下一次恢复。本体故障、控制来源改变、断线及实体 B/L2、网页停止仍按原停止逻辑处理。当前参数已做离线检查，未执行真机恢复试验。

Dex3 的健康反馈检查只包含 SDK 故障、有效数值与通信时效，位置越界单独提示；手部反馈异常不阻止接管底层、机身准备或策略运行。正常手部控制中 SDK 故障、无效反馈或反馈超过 200 ms 未更新，只暂停双手轨迹并警告；手部 DDS 写入返回失败或抛出异常也独立处理，继续尝试发送双手 Kp=0、Kd=0.1 的阻尼指令，不触发机身全局停止、不释放机身控制权。手部专用 DDS 通道初始化失败同样只警告。通信故障期间无法保证手部阻尼命令已到达电机。阻尼停止、持有者断线、实体 L2、桥接心跳超时和程序退出均中断手部轨迹，以 Kp=0、Kd=0.1 退出。正常手部控制从 [`config/dex3_pd.json`](config/dex3_pd.json) 读取参数，默认 **Kp=1.5、Kd=0.2**，双手全部 14 个关节共用，首次使能抓握、后续归零／抓握及补偿动作均使用这组参数；继续启用电机通信超时位。只读模式不发布机身或手部命令，离线模式不连接 DDS。手部姿态切换不修改机身关节目标；进入策略后腰 yaw 和双臂都保持准备目标。

已经使能过的手部发生故障后，通信恢复不会自动续跑旧动作。准备完成或策略运行时，按钮改为 **Dex3 重新启用并归零（3 秒）**；双手反馈健康后明确点击，才从当前实测角度平滑归零，按当前勾选状态应用文件补偿。之后恢复抓握／松开切换。机身仍按原目标与增益控制；机身本身的健康故障、机身通信故障和显式停止继续按原停止逻辑处理。`DEX3 CONTROL warning/resumed` 记录手部暂停和重新启用，`DEX3 TRANSPORT` 记录手部通信故障与恢复。

调整 Dex3 PD 时直接编辑此文件，再退出并重启整个网页程序：

```json
{
  "schema_version": 1,
  "kp": 1.5,
  "kd": 0.2
}
```

配置在程序启动时加载一次，重新接管底层仍使用本次加载值；修改文件不热更新正在运动的机器人。也可用 `--dex3-pd-config /绝对路径/pd.json` 指定文件。`kp` 必须大于 0，`kd` 必须非负，均须为有限 float32 数值；文件缺失、字段错误或数值无效时启动直接报错。正常 PD 不覆盖停止参数。网页“运行记录与频率”显示本次加载值，`metadata.json` 的 `dex3_pd` 保存控制参数及停止参数，`bridge.log` 的 `DEX3 PD` 在左右手各自第一次成功下发及进入阻尼时记录实际指令使用的增益。日志元数据仅保存这些必要参数，不复制配置文件。

手部反馈兼容 `rt/lf/dex3/{left,right}/state`（本机已有控制程序使用的话题）和 `rt/dex3/{left,right}/state`；优先使用新鲜的 `rt/lf` 反馈，另一话题仅在其缺失或过期时接替。命令始终发往 `rt/dex3/{left,right}/cmd`。手部未就绪时仍可准备机身，状态区与左侧告警提示手部问题；本次会话 `bridge.log` 的 `DEX3 HEALTH` 行给出左右手实际选用的话题、反馈延迟、未就绪原因（未收到数据、过期或报错）及位置越界警告，不再只显示一个健康布尔值。

网页和 `dex3.blocking_reason` 说明未收到反馈、超时或 SDK 异常。位置越界由左侧监视面板单独提示：例如右手 `thumb_1=-1.1186 rad` 低于警告下界 `-1.0700 rad`，会标红该关节并显示警告，准备按钮仍可用；运行中的机身控制继续。`DEX3 HEALTH` 可以同时显示 `healthy=true` 和 `reason=joint_out_of_bounds`，分别表示 SDK/通信健康和位置警告。位置余量不扩大目标限位；电机报错等需查看 `bridge.log`。

部署包的 `HandState_` / `PressSensorState_` 定义已与本机 `/home/unitree/code/unitree_sdk2` 同步，触觉传感器包含 `lost`、`reserve` 字段；`cpp/dex3_type_support.cpp` 同步覆盖随附旧静态库中的触觉字段表。仅修改话题名或头文件不足以解决旧版本的 DDS 类型不匹配。构建时的 `hand_dds` 离线测试检查完整报文解码、重新编码及 DDS 类型标识，不连接机器人；更新后需重启网页程序才能加载新桥接。

Homie 模型内部已经包含 HIM 速度估计器：6 帧历史生成 3 维速度估计和 32 维隐变量，与最新观测一起送入动作网络。外层现在从同一次 Homie 推理中读取并记录 12 维腿部动作、3 维原始速度估计、32 维原始隐变量和归一化隐变量；估计器输出仅供记录分析，尚未接入平移外环。估计值不能当作传感器实测速度。

- 默认 `--policy-mode auto`：滤波后原单位速度命令范数达到 `0.05` 时使用 Homie；低于阈值的同一拍选择 Balance 并输入当前零命令。无精确零命令等待、无关节速度/IMU 静止门槛。
- `--policy-mode balance` / `homie` 可固定单模型。无论选择哪个模型，两套观测与影子推理都保持更新。

- Balance、原 Homie、推车学生及配套微调 HIM/Homie 分支在启动时完成加载与首次推理预热，准备阶段持续积累历史。每拍只执行当前 Homie 分支。低层为 6 帧，推车为 5/32 帧，推车需要有效 ID 0/1 航向；未启用时只影子推理，启用时保留有效历史。
- 两套 PD 分别读取 `config/balance_pd.json` 和 `config/homie_pd.json`，策略切换直接使用目标 PD 和新动作。`profile_transition_s=0`、`policy_target_speed_rad_s=0` 分别关闭旧目标混合和正常策略目标变化率限制；准备姿态的渐变、关节范围和名义 PD 力矩限制仍生效。命令范围为 vx **[-0.8, 1.2] m/s**、vy **[-0.5, 0.5] m/s**、wz **[-0.8, 0.8] rad/s**。

- 网页松手和导航指令超时保留 250 ms 检测；导航只按原始命令时间判断新鲜度，UDP 重传不续期。导航零命令、关门也使用上述滤波。减速期间不增加幅值、不反向、不产生新纠偏，排队运动不能打断。实体 B/L2、持有者断线、故障、阻尼停止和 EXTERNAL 来源超时仍按原逻辑立即停止。

外层保持 `G1_URDF/g1.urdf` 的单腰结构：27 个可动关节，SDK 索引仍为 0–12、15–28。外层启动桥接传入 `--single-waist`，SDK 13/14 不使能、目标和增益为零；29–34 也不使能。两套模型均观测这 27 个关节，只输出 12 个腿部动作；腰 yaw 和双臂保持 YAML 准备目标，切换模型也保持。无网页默认入口仍使用 29 个 SDK 槽位，腰和双臂保持接管时姿态。

真机模型使用实测关节角与 IMU，根位置固定，可调显示高度；没有世界位置或实测速反馈。离线模式使用合成关节反馈，同样没有真实根位移，不能用于验证行走稳定性。

### 左侧关节监视面板

停靠在网页最左侧，点击标题栏 «／» 可整体收起或展开。仅保留“关节角度”和“告警信息”两个可独立折叠的区域，已删除模型图片区域。

本体 27 个关节及左右 Dex3 各 7 个关节按腿部、腰部、手臂、Dex3 分组，左右并排，合计 21 个数据行。只显示**下发角度和误差**，统一为 **°**，约 5 Hz 刷新。表格不设置内部滚动条，普通桌面窗口可尽量一次看全；较矮窗口仍可能需要滚动整个侧栏。实际角度继续用于计算、超限检查和运行记录。

- 误差 = 下发 − 实际。`config/joint_monitor.json` 的 `error_threshold_deg` 默认 **5.0**；绝对误差严格大于该值时，对应关节的三个单元格标黄。修改配置后重启。该阈值仅用于提示，不改变控制或停止条件。
- 位置超限优先标红并加 `!`；腿部、腰部、手臂及 Dex3 全部按警告级别显示，不触发全局故障、不撤掉全身位置增益，也不阻止接管或发起机身准备。不可比较、反馈过期或未启用位置控制时误差显示 `—`，不会误标黄。
- 告警区域可独立滚动；已结束告警淡色保留 5 秒，同一关节变化的数值更新原告警，避免刷屏。

超限判定与 C++ 桥接的位置告警一致，不在运行时从网页 URDF 读取：本体用 `deploy.json` 的 `joint_lower/upper_sdk29`，Dex3 用指令限位，均加 0.02 rad 反馈余量。Dex3 常量与[官方示例](https://github.com/unitreerobotics/unitree_sdk2/blob/main/example/g1/dex3/g1_dex3_example.cpp)的左右手数组一致，官方将其标为 URDF limits；这些模型/配置范围仅作为软件参考，不能当作实机硬件故障边界；超出参考范围只报警，后续控制指令继续执行。告警来源：

| 告警 | 来源 |
|---|---|
| 关节位置超限 | Python 按上述参考范围实时检查实测角；桥接 `BODY POSITION`／`DEX3 HEALTH` 行，仅为警告 |
| 机身请求目标越界／位置与 PD 力矩约束冲突 | `BODY TARGET`／`BODY EFFORT` 行，仅为警告；目标限幅／仅降低对应关节增益 |
| 准备姿态超过 10 秒未到位 | `CALIBRATION warning holding_position_control`；快照 `preparation_warning` 显示关节偏差，事件记录警告开始及解除；持续位置控制，实测到位后解除 |
| 电机温度过高（> `max_temperature_c`）、电机报错（`motorstate≠0`） | 官方 SDK `LowState_.motor_state[].temperature/motorstate`，由 C++ 桥接判定后写入本次 `bridge.log`；机身过温记录全部超温关节的 SDK 编号、两路温度和阈值，网页显示中文关节名、完整关节名、SDK 编号及该电机最高温度 |
| Dex3 恢复超时或恢复中止 | `bridge.log` 的 `DEX3 RECOVERY warning`，仅结束手指恢复 |
| Dex3 温度、电机报错、`HandState.error`、反馈超时 | 官方 SDK `HandState_`，同上 |
| 机身倾角过大、LowState/IMU/遥控异常、底层故障停止 | `bridge.log` 的 `HEALTH`／`STAGE` 行 |
| 反馈延迟、阻尼／故障停止原因、记录异常 | Python 控制器快照 |

机身请求目标仍限制在配置参考范围内：有限值越界会限幅并警告，不再以 `invalid target` 触发全局停止；NaN/Inf 等无效数值继续拒绝。若实测角度偏离过大，导致参考目标范围与名义 PD 力矩范围没有交集，保留限幅后的目标，仅按比例降低该关节 Kp/Kd，使计算的 PD 力矩不超过配置 effort；其余关节持续控制。恢复后重新使用正常增益。该约束是主机侧计算，不等同于电机实际力矩测量。

位置警告与其他停止原因分开：机身 SDK 电机故障、过温、反馈/指令心跳超时、无效数值、机身倾角异常和显式急停仍执行原保护。准备仍要求实测到位，准备不到位超时只警告并继续保持位置控制；位置告警本身不阻止准备或策略运行。

网页只读地追踪本次会话目录中的 `bridge.log`，不改变 C++ 判定。[官方 `hg/MotorState_` 定义](https://github.com/unitreerobotics/unitree_sdk2/blob/main/include/unitree/idl/hg/MotorState_.hpp)提供 `temperature`、`motorstate` 和 `tau_est`（估计力矩），没有电流字段；当前接口也没有提供已核实的过流故障码映射，因此暂不显示“电流过大”告警。估计力矩不会被当作电流。桥接未把各电机温度值通过本机 UDP 上报，温度告警由桥接阈值触发（本体 > 阈值，Dex3 ≥ 阈值）。机身过温告警显示触发时的温度，故障停止信息保留当时的关节及温度，即使随后温度恢复也可追溯；这不是连续实时温度显示。旧版日志没有关节/温度明细时明确标为未记录，不能追溯推断。无记录日志的离线模式只有 Python 侧告警。

## 骨盆 IMU 与实时 wz 修正

`vx/vy` 始终沿当前机身轴。骨盆 IMU 来自 `rt/lowstate.imu_state()`，独立分支处理姿态和角速度，仅修改策略物理单位 `wz`，随后由原观测构造乘一次 `0.5`。不旋转 XY，不修改两套模型的原始 IMU 观测、权重、动作缩放或关节 PD。

- 前进、后退、左右侧移和斜走且无主动转向：进入时捕获当前骨盆 yaw，保持该朝向。
- 原地旋转或边平移边转弯：立即释放旧参考，不用航向保持抵消用户转弯。回零去抖、角速度减小或达到有限等待时间后，捕获新的朝向。
- yaw 使用 SDK 四元数，不增加重低通；角速度独立做 3 Hz 一阶低通，只在新的状态样本到达时更新。实际控制 dt 与接收 dt 分开使用。
- 手动“速度归零”、网页松手和导航停车均使用部署配置的 0.4 秒命令滤波；B、急停、断线和共享 IMU 故障优先立即停止。
- 姿态参考跳变或超出反馈小倾角范围：释放参考，受限退出纠偏；健康数据恢复并回零后才能重新锁定。

[`config/motion_config.json`](config/motion_config.json) 按用户最新要求默认 `run_mode=active`，行走和推车共用航向参数。`shadow` 只记录建议，不改变策略命令；`disabled` 关闭纠偏。沿用之前实机使用的 Kp=1.0 s⁻¹、Ki=Kd=0、纠偏上限 0.15 rad/s；新的推车接入尚不能据此宣称已完成真机验证。网页在速度归零后可修改模式、Kp、上限和角速度截止频率；设置只影响本次运行。显式 `--heading-mode` 优先于配置，单独 `--heading-kp` 不覆盖模式。

推车命令来源为 `PUSHCART`，骨盆参考航向跟随高层给出的机器人角速度推进，再叠加 Kp 纠偏送入 Walk/Balance。

## 运行记录与测试

左侧面板的下发值取自 C++ 最近一次成功写入 DDS 的电机指令，包含准备／手部切换的插值和所选按钮的补偿；不是 Python 请求值或最终姿态目标，也不代表电机已确认接收。只读或尚未下发时指令显示 `—`；Kp=0 阻尼、反馈异常或记录过期时不计算误差。离线模式明确标注合成数据。

`observe`、`control` 自动保存机器人本体运行数据，合并只保留最近 5 次有反馈的会话，第 6 次有数据后删除最旧一次。空启动不占名额。

```text
logs/sessions/UTC时间_模式_编号/
├── metadata.json       # 本次参数、配置标识和航向设置
├── telemetry.jsonl.gz  # 反馈、IMU、速度命令、关节目标/增益、模型和估计器输出、时序
├── events.jsonl.gz     # 网页操作、参数修改、停止与异常
├── bridge.log          # C++ 运行日志
└── summary.json        # 正常退出时写入条数、耗时和错误
```

不保存模型文件、源码、URDF、网格或配置文件快照，不保存每帧网络完整输入历史；模型输出必须保留。记录采用压缩后台写盘，按每次 Python 策略采样记录，不是全部 200 Hz DDS 报文；实际频率见日志中的 `timing`。当前 schema 18（含实际 Homie 估计器来源及推车候选/采用命令），`dex3` 保存左右手健康状态、目标姿态、过渡进度、14 维实测 q/dq 与指令 target（左手在前），并区分 `open`（全零）、`grasp`（原抓握）、`open_compensated`（补偿归零）与 `grasp_compensated`（补偿抓握）；保留的旧会话仍按原 schema 解释，未正常结束的会话没有 summary。

推车时 `homie_estimator_source=pushcart_finetuned`，退出推车为 `homie_original`。
`homie_estimator.velocity_raw` 记录实际输入 Homie actor 的三维速度估计，`velocity_original_raw` 记录同帧原 HIM 估计；
两种模式的 32 维隐变量都来自原 HIM。推车使用学生模型配套的微调估计器，详见[推车说明](../G1_high_policy_deploy/README.md)。
推车日志同时保存小车任务命令、高层候选机器人速度、Viser 归零/滤波后的速度、腿部与腰臂候选残差及采用情况。
`high_policy.inference_inputs` 标明本次推理使用的机身 tick、相机采样时间/航向、上一拍命令和上肢 PD 力矩估计；
`inference_started_monotonic` / `inference_finished_monotonic` 是学生 ONNX 的开始/结束时间。
这些字段与同一行的机身反馈、低层输出、请求关节目标一起分析；C++ 实际下发目标仍按其发送时间单独对齐。

每帧新增 `joint_comparison`，其中 `command_rad`、`actual_rad`、`error_rad`、`valid`、`position_control` 均按 `metadata.json` 的 `joint_comparison.joint_names` 排列，共 41 项；SDK 13/14 两个固定腰部槽位不参与。未下发／未收到反馈的角度为 `null`，无效误差为 `null`；旧角度可保留，但 `valid=false`。`sent_ns` 和 `feedback_ns` 分别记录机身、左手、右手三个组的最近发送成功／反馈接收时间；`sampled_ns`、`bridge_ns` 为 Python 采样和 C++ 回包时间，均为本机 monotonic 纳秒。对比的是最新指令与最新反馈，时间并非严格同步，运动中的差值可能包含跟随延迟，不能直接当作静态零位偏差。

`tools/inspect_session.py` 自动汇总每个关节有效位置控制样本的平均绝对误差、均方根误差和最大绝对误差（rad），默认读取最新会话，也可传入会话目录；保留原有模型、运行频率和航向分析输出。

每帧 `telemetry.jsonl.gz` 的分析字段：

| 字段 | 含义 |
| --- | --- |
| `model_actions.balance` | 12 维腿部网络原始动作，裁剪/缩放和关节限位之前；旧 schema 13 为 15 维 |
| `model_actions.homie` | 12 维网络原始动作，裁剪/缩放和关节限位之前 |
| `homie_estimator.velocity_raw` | 3 维估计器原始速度分支输出，顺序 x/y/z；微调分支已核实除以 2 为骨盆机身系估计 m/s；原分支仍保留原始单位 |
| `homie_estimator.latent_raw` | 32 维原始隐变量 |
| `homie_estimator.latent_normalized` | 实际送入 Homie actor 的 32 维 L2 归一化隐变量 |
| `policy_inference_monotonic` | 本次推理完成时间；配合同帧 `state.tick`、`state.received_ns`、`policy_steps` 对齐反馈 |
| `selected_model` | 当前选择的策略；另一套输出仍作为影子推理结果保留 |
| `requested_target` / `target` | Python 请求的关节目标 / C++ 回报的实际应用目标，可能相隔桥接周期 |

准备过程或停止后没有新推理时，输出及推理时间均为 `null`，不能拿上一帧当新结果。`metadata.policy_outputs` 保存字段定义、关节顺序、动作缩放和源模型 SHA-256，方便辨认模型版本，无需复制模型。Homie 输出只在内存中增加读取接口，不修改磁盘原模型。

旧记录中已经清理掉的原始模型输出无法从关节目标准确还原，过去未采集的 Homie 估计输出也没有补写；上述字段从新版运行开始记录。

`--record-dir` 可修改会话目录，仍仅保留最近五次。sim 默认不记录；明确需要时用 `--record-sim --record-dir /tmp/viser-sim`，不得混入真机 logs。`--log /tmp/viser-export.jsonl` 可显式导出调试数据，默认不产生重复日志。

`observation_to_action_ms` 是 Python 观测构造至推理完成；`state_to_command_ms` 则包含从 C++ 接收机身反馈到 Python 发出指令的时间，
只读/未接管时为 null，仍不包括随后 DDS 下发及真实电机响应。网页诊断区显示这两种延迟。

### 推车上肢 PD

启用推车时，腰 yaw 使用 300/3，肩 pitch/roll 100/2、肩 yaw 50/2、肘 50/2、三轴腕 20/1（Kp/Kd）。
参数在相邻部署包 `config/pushcart_upper_pd.json`；进入和退出都渐变 0.5 秒，网页会提示，完成后才能发送新速度。
C++ 在推车模式执行腰臂修正，返回普通行走后保持最后上肢姿态并恢复原增益。
该切换不修改腿部模型选择，也不改手指抓握角度或 Dex3 PD。通信协议为 v9，更新后需完整重启 Viser。

推车腰 yaw 和双臂目标使用 20 ms 线性插值：策略约 50 Hz 更新终点，C++ 每 5 ms 下发一个中间目标。
正常 200 Hz 时，0.06 rad 的变化分为四次约 0.015 rad；新目标提前到来时从最后下发值接续，
目标迟到则保持已完成终点，不外推。上肢增益过渡期间保持位置，完成后才开始插值。
归零、暂停或退出推车立即取消未完成的上肢轨迹；实体 B 在 C++ 冻结上肢目标，L2/阻尼停止/故障仍优先。
腿部保持原直接目标，手指使用自身控制逻辑。`pushcart_upper_pd.json` 中
`target_interpolation_s` 为 `0.02`，设为 `0` 可恢复直接目标；两种设置都需完整重启生效。
这是为改善真机目标阶跃新增的执行平滑，会改变训练时保持目标的响应时序，需要实机比较抖动和跟踪效果。
日志 `requested_target` 是策略终点，`target` 和 `joint_comparison.command_rad` 是采样到的底层实际输出；
上肢力矩观测也使用实际下发目标。自动日志仍按 Python 策略拍采样，不保存每个 200 Hz 子步。
